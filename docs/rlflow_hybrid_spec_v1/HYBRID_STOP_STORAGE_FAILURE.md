# 原进程在账本故障下的 STOP 与恢复

Checkpoint 66 处理关键账本读写失败不能阻断原进程回收的问题。它延续已批准的固定 CPU 和工程任务、原共享 Pool 与认证 STOP；不增加模型、GPU、任意命令或生产迁移权限。基线为 Checkpoint 65 的 `27ad05b`，Checkpoint 41 已完成，不重新开启。

## 交付行为

正常 STOP 仍先记录持久冻结再中断原进程。若 Project 或 Pool 记录失败，Runtime 先锁存原 participant 停止与不可逆的效果冻结，再用原 lease、原 source、原 PID 身份和 pidfd 完成信号、回收及 FD 清理。账本错误仍返回 UNKNOWN 或 HTTP 503；这条物理安全路径不能生成终态、释放 Pool、退款或重新派发。

source 关闭失败不会跳过原工程输入 FD。owner 安全关闭会尝试所有原 source、工程输入、候选 material 与 claim FD；任一部分失败都保留原 owner 供原能力重试。即使物理清理最终完成，owner 安全关闭也只报告 `PHYSICAL_CLOSED_EXPOSURE_UNKNOWN`，不是可退款或已释放槽位的事实。

认证整组 STOP 的接受记录写入失败时，原 operation 保存已经尝试的清理结果。coordinator 复用该首次结果，不再自动调用第二次取消。普通重试仍是原回执语义，未知 scope 的继续清理须使用原 key 的显式恢复。

## 原提交的恢复边界

只有当前原 cleanup 写入事务实际成功回滚，且 guard、db、精确记录、已尝试写入与单一 STOP 阶段全部一致，才保留私有回滚见证。明确没有新增控制接受字段、事件与 projection 均不存在时，原 cleanup 才能重新链接到当前 CAS。原 lease、阶段和确定性 key 不变，不能获得新执行许可。

每次实际新写入前消费旧阶段的回滚见证，只能由本次实际成功回滚重新签发。真实 COMMIT 已完成但返回丢失、rollback 失败、CAS 在写入前冲突以及控制接受不确定均不能生成该见证。前置读取或 CAS 拒绝尚未尝试新写，不消费原已证见证。已提交记录通过原精确记录确认，不重写历史；未知提交保持不可变并继续保留暴露。participant 停止锁存只限制 spawn 与 G，正常工程 STOP 后的原 core apply 不由此误冻结。

## 验收与当前验证

验收要求实际原有子进程在故障期间存活，随后被原能力回收；FD 关闭失败须保留重试能力，未持久确认时占槽不释放；最后效果门禁止后续 spawn、G 或工程写入。同一 STOP key 恢复不能新增 Popen、重复接受事实或影响另一项目。未知 COMMIT 与失败 rollback 必须保持原记录不重建。整组接受失败只自动清理一次，正常工程单次写入与机器 AST 验证保持有效。

16 项新增验收采用分轮定向合成证据：原 13 项覆盖 Project、Pool、部分 FD 的 SDK 实际进程、HTTP 503 与同 key 恢复、无 Unit 清理、整组一次清理、真实 COMMIT、工程输入、rollback 与两条原 source；最后 3 项覆盖先有回滚见证再丢失 COMMIT 返回、再次 rollback 失败，以及真实工程结果后的终态 rollback 与 CAS 恢复。该工程结果恢复 terminal 和 Pool FREE 后，既有安全冻结仍精确拒绝 apply，实际 pwrite 为零，候选源码保持原字节。这不是最后重跑整个新模块的声明。首次恢复失败与测试夹具错误均保留原日志，修复后只重跑失败项。

唯一必要八模块回归实际 126 项通过，2 条既有告警，耗时 1414.95 秒，包含正常工程 STOP 后单次 core apply 和 AST 21 项验收。结束并校验冻结输入后，仅修复旧回滚见证寿命；最后 3 项定向实际通过，耗时 29.87 秒。其余 329 路径不变，不重复成功回归或 UI 测试。最终 331 输入全部匹配，编译、依赖与差异检查通过，独立 High 增量审查无剩余必须修复项，无运行中测试。完整命令、失败诊断、终态与原日志哈希见 `evidence/checkpoint-66-final-tests.txt` 和 `evidence/checkpoint-66-log-sha256.txt`。
